# SuperOpt

A macOS menu bar app that repurposes the Option key and adds GNOME-style hot corners.

**Keep this file up to date.** When adding features, changing architecture, or learning new project conventions, update the relevant sections below so future sessions have full context.

**Privacy: This app must never make network requests, collect telemetry, phone home, or transmit any data.** All processing is local. Do not add dependencies, analytics, crash reporting, or any code that communicates over the network.

## Features

- **Single press `⌥`** → Toggles Mission Control (by emulating the Mission Control key, virtual key code 160)
- **Double press `⌥`** → Toggles the Spotlight Applications section (by emulating the Apps key, virtual key code 131)
- **Hot corner** → Slamming mouse to top-left corner of any screen opens Mission Control with a GNOME-style ripple animation
- **Opt+1–9** → Launches the Nth app in the Dock (position 1 = Finder, then persistent-apps from `com.apple.dock.plist`). Consumes the keypress so no special character is typed. "Finder Position" submenu lets you place Finder at any slot 1–9 (default 1), shifting other apps to fill the gap. Disabled when parent feature is off.
- **Caps Lock OSD** → Shows a centered on-screen notification ("⇪ Caps Lock On/Off") when Caps Lock is toggled, inspired by gnome-shell-extension-lockkeys
- **Home/End remap** → When a text field is focused, Home/End keys move the cursor to the start/end of the line (like Windows/Linux) instead of scrolling. Ctrl+Home/End jumps to the document start/end (Cmd+Up/Down). Only ⌃ and ⇧ combine with Home/End here — ⌥Home and ⌘Home are left to whatever the app binds them to. Uses the Accessibility API to detect focused text fields. Preserves Shift for text selection.
- **⌥A → Apps** → Option+A opens Spotlight Apps (same as double-press Option). Own UserDefaults key (`appGridEnabled`). Enabled by default.
- **Shortcut Remapping** → Maps Linux keyboard shortcuts to their Mac equivalents. Organized into categories (General, File, View, Text Editing, Finder, Tabs & Windows, Browsers, Terminal, Code Editor) with per-shortcut toggles in disclosure groups. Includes: Ctrl+C/X/V/Z/A/S/N/F/P/R/T/W/L etc. → ⌘ equivalents, Ctrl+Y → ⇧⌘Z (Redo), Ctrl+Q → ⌘Q (Quit), Ctrl+Delete → ⌥Delete (delete word), Ctrl+⌦ → ⌥⌦ (forward delete word), Ctrl+Left/Right → ⌥Left/Right (word navigation), Alt+F4 → ⌘W (close), Alt+L → ⌃⌘Q (lock screen), Alt+Enter → ⌘I (Properties). Finder-specific: F2 → Rename, ⌦ → Move to Trash. Browser shortcuts: Ctrl+R (reload), Ctrl+Shift+I/F12 (DevTools → ⌥⌘I), Ctrl+H (history → ⌘Y), Ctrl+Shift+P (private window, Firefox). Terminal shortcuts: Ctrl+Shift+C/V/W/Q/T → ⌘C/V/W/Q/T (only in terminal apps). Terminal apps pass through plain Ctrl+A/C/D/E/L/U/W/Z unchanged. "Detect Integrated Terminals in Code Editors" (`vscodeTerminalEnabled`, off by default) extends that to the terminal panel in VS Code, VS Code Insiders, VSCodium, and Cursor; its row stays visible while the setting is on even with the master toggle off, since the detector (and the Chromium accessibility opt-in it carries into the editors, and Home/End's terminal skip) runs as long as its key is set — hiding it with the parent off would leave it active with no way to turn it off. Code Editor shortcuts: Ctrl+H → ⌥⌘F (Find and Replace), Ctrl+/ (comment), Ctrl+] / Ctrl+[ (indent/outdent), Ctrl+Shift+Up/Down → ⌥Up/Down (move line), etc. — only active in VS Code, Cursor, JetBrains, Zed, Sublime Text, Nova. Finder, Browsers, Terminal, and Code Editor categories are app-gated — shortcuts only fire in the matching app. A chord claimed by both a gated category and an ungated one is owned by the gated category when the two map it differently: disabling it there restores passthrough rather than falling through to the ungated category's mapping of the same chord (the terminal chords, the code editors' ⌃⇧↑/↓, and the browsers' ⌃⇧I follow this; ⌃U's View Source and Underline map to the same ⌘U and share one table entry, so there is nothing to own). Disabled shortcuts stored in `gnomeDisabledShortcuts` UserDefaults array. Master toggle and all shortcuts disabled by default.
- **Cut & Paste Files in Finder** → Emulates GNOME-style file cut & paste. Ctrl+X copies files and marks for move, Ctrl+V moves instead of duplicating (posts ⌥⌘V). The move only happens when Finder's own copy landed on the pasteboard — its change count must be exactly +1 from the cut, have moved within a 200 ms confirmation window of the cut (Finder posts its pasteboard write within tens of milliseconds; a copy the user makes after an empty-selection cut — ⌘C, the Edit menu, another app — is a selection and a keystroke away, so a later +1 is never misread as the cut's own; the check also runs synchronously at paste time so a paste faster than the watch's first tick still moves), and the pasteboard must hold file URLs (a prompt +1 of anything else — text or images from a background writer such as Universal Clipboard or a clipboard manager — is nothing Finder could move; a background writer that itself lands file URLs within the window remains indistinguishable from the cut's own copy, an accepted residual: no API names a pasteboard change's author); a stale cut (empty selection, unconfirmed copy, or the copy not yet processed) falls back to an ordinary ⌘V paste so nothing the user did not cut is ever moved. Ctrl+C cancels pending cut. Only active in Finder when no text field is focused. Own handler class (`FinderCutHandler`), own UserDefaults key (`finderCutMode`). Disabled by default.
- **Middle-click Paste** → Context-aware middle mouse button matching GNOME/X11 behavior. Emulates the X11 primary selection: the text selected in the focused element is read via `kAXSelectedTextAttribute` *before* anything clears it, then typed at the click point with `KeyboardUtils.postText`; with no selection it falls back to a clipboard paste (⌘V). AppKit text views ignore middle clicks — the caret never moves — so for a classified text-field target the middle click is consumed (its release too, so no phantom `otherMouseUp` reaches the app) and replaced by a synthetic left click at the same point, which positions the caret; because a left click on an inactive window (another app's, or another window of the frontmost app) is swallowed as bare activation, the target window is raised first and the click waits until it is genuinely in front, aimed at the window the click was classified against. Chromium editors cannot be classified at tap time — they hit-test as plain `AXGroup`s and answer no focused-element query while backgrounded — so for unclassified targets the real click is let through and a deferred re-check runs once the app under the point has come forward, raising it after a short grace if the click's own activation did not and only while focus has not moved to a third app, opting the app into `AXManualAccessibility` the way `ElectronTerminalDetector` does. The focused-editor classification (`focusedTextElement` + the ancestor-walk bounds check) is gated on the `AXDOMClassList` engine discriminator (answered by Chromium and WebKit alike; AppKit and Gecko are not) at both its call sites: AppKit and Gecko apps expose real structure under the pointer, and their focused element's ancestors can span unrelated UI — a tab bar sharing a container with the focused text view — which the bounds walk would cover and classify as a paste target (a middle click on a Terminal or Firefox tab while text is focused pasted instead of passing through before the gate). Safari page content passes the gate — an accepted residual: only a click inside the focused field's own ancestor groups can misfire there, and no AX attribute separates WebKit from Chromium. A Chromium *source* hides its selection from AX entirely, so its selection is copied with a ⌘C at click time while the source still has focus (detected via the private `AXDOMClassList` attribute; on the deferred path only for a background window of the *same* app — the VS Code window A → window B case — since a cross-app target's activation races the copy in a way the wait cannot attribute). The paste waits for the pasteboard's change count to move before focus shifts, and honors a moved count only while focus never left the source app and window — a copy that landed after focus moved copied the wrong selection and the paste is abandoned; an unmoved count at the timeout means nothing was selected, and the ordinary clipboard fallback proceeds, exactly as for an AppKit source. In-flight chains are abandoned (a generation counter checked at every side effect) when the feature is turned off or an app is excluded mid-flow; `reset()` mirrors `ClickThroughFocusHandler`'s. On Dock app icons, opens a new window (activates the app and posts ⌘N, or just launches if not running; for an app with windows, waits for the app to come frontmost for up to one second (polling, via `AppActivation`), then posts ⌘N only if the app is frontmost). On other Dock elements, consumed with no action. Non-text-field clicks pass through unchanged (browsers get native open-in-new-tab, other apps get default middle-click; password fields are never targets). Own handler class (`MiddleClickPasteHandler`, delivery machinery in `MiddleClickPasteWindow.swift`), own UserDefaults key (`middleClickPasteEnabled`). Disabled by default.
- **Click-Through Focus** → Linux/Windows-style focus-on-click: one click on an inactive window both brings it forward and reaches whatever is under the pointer, instead of being swallowed as a bare activation click. Covers both a window of another app and another window of the frontmost app (the two-browser-windows case). The press (and its release, if it arrives first) is withheld at the event tap, the target window is raised and focused, and the press is replayed once the window is actually in front. A press arriving while one is still withheld abandons the withheld press and is itself evaluated through the normal path — a double-click on a slow-activating window is not delivered half-swallowed; the abandoned press's release needs no matching, because on a single pointing device a second press cannot precede the first's release through a working tap (an unreleased pending at that point means the release was missed while the tap could not see events, and it has already reached the window on its own). Title bar presses are left alone so dragging still works, as are presses in the few points just outside another window's frame, which are that window's resize border. Not focus-follows-mouse — hovering does nothing. Own handler class (`ClickThroughFocusHandler`), own UserDefaults key (`clickThroughFocusEnabled`). Disabled by default.
- **Scroll Zoom** → Ctrl+scroll zooms in and out in browsers. Supports natural (scroll up = zoom in) and traditional (scroll down = zoom in) scroll directions via a picker (Off/Natural/Traditional). Own handler class (`ScrollZoomHandler`), own UserDefaults key (`scrollZoomMode`). Disabled by default.
- **Window Tiling** → Option+Arrow keys tile, maximize, or restore windows by triggering native macOS tiling via Accessibility menu item pressing. Option+Up → Fill, Option+Down → Return to Previous Size, Option+Left/Right → Left/Right half. When the matching menu item is greyed out the keystroke is passed through to the app instead of being consumed. Own handler class (`WindowTilingHandler`), own UserDefaults key (`windowTilingEnabled`). Disabled by default.
- **Tile Assist** → Detects when the focused window tiles to the left or right half of the screen (via AX move/resize notifications from `TileAssistWatcher`) and shows a popup in the remaining free space with other windows that can fill the gap. Works with any tiling method — keyboard shortcuts, drag-to-edge, menu bar items, third-party tools. Clicking a window activates it and tiles it via the Arrange menu item. Dismissed by Escape, clicking outside, focus change, window resize, turning the feature off, or 5-second timeout. Independent of Window Tiling feature. Own class (`SnapAssistPanel`), own UserDefaults key (`snapAssistEnabled`). Disabled by default.
- **Green Button Fills Screen** → Clicking the green traffic light fills the window to the visible screen area instead of entering full screen. Clicking again restores the previous window size. A window already in full screen keeps the stock behavior — the click passes through and leaves full screen, since there is nothing to fill or restore there. Mission Control clicks pass through too — its shield hides the windows while their AX frames stay logical, so the hit test could resolve a button that is not visually there. Uses Accessibility API to detect the green button (`AXFullScreenButton`/`AXZoomButton` subrole), find the parent window, and press the native Fill / Return to Previous Size menu items via `WindowTilingHandler.pressMenuItem`. Own handler class (`ZoomButtonHandler`), own UserDefaults key (`zoomButtonEnabled`). Disabled by default.
- **Menu Key → Shortcut Menu** → The Menu/Application key on PC keyboards (key code 0x6E) opens a context menu. When a text field has a collapsed caret, the caret's screen position is read via the `kAXBoundsForRangeParameterizedAttribute` AX attribute and the menu is opened there. When text is selected, falls back to `AXPerformAction(kAXShowMenuAction)`, which opens the menu mid-element but leaves the selection intact. Otherwise right-clicks at the mouse position. Own handler class (`MenuKeyHandler`), own UserDefaults key (`menuKeyRightClickEnabled`). Disabled by default.
- **Close Windows in Mission Control** → GNOME-style close buttons on window thumbnails in Mission Control. A close button (dark circle with white X) appears at the top-right corner of the hovered window thumbnail. Turns red on hover over the button. Hover accepts the thumbnail or the button's padded hit rect, and click accepts the same padded rect, which extends past the thumbnail's corner, so the drawn button's outer half is reachable. Click is intercepted via the CGEvent tap (before the Dock can focus the window) and closes the window via its AX close button. Skips windows without an AX close button (modals, sheets). Uses `CGSGetScreenRectForWindow` private API for live thumbnail positions. Position updates share the Mission Control monitor's 4 Hz tick while thumbnails are stable. A separate timer follows moving thumbnails at the display refresh rate. Its position timer stops when Mission Control closes. Own handler class (`MissionControlCloseHandler`), own UserDefaults key (`mcCloseEnabled`). Enabled by default.
- **Type to Search in Mission Control** → GNOME-style: typing while Mission Control is open closes it and opens Spotlight prefilled with what was typed. A picker (Off / Spotlight / Apps) chooses whether the regular Spotlight search or the Spotlight Apps view opens. The first printable keystroke is consumed, Mission Control is dismissed by posting the Mission Control key, the Spotlight key (177) or Apps key (131) is posted, and every keystroke typed in the meantime is buffered and injected once Spotlight's field is focused. Own handler class (`MissionControlSearchHandler`), own UserDefaults key (`mcTypeToSearchMode`). Disabled by default.
- **Scroll the Apple Menu to Switch Spaces** → Scrolling the Apple menu moves that display to the next or previous space, the way scrolling GNOME's panel switches workspace. Works by posting the system's own "Move left/right a space" shortcut, so it needs that shortcut enabled (it is by default) and follows whatever the user has rebound it to. macOS applies it to the display under the pointer, which is the display whose Apple menu was scrolled. One wheel notch is one space, as in GNOME; a trackpad has no notches, so its travel is added up until it amounts to a gesture. Own handler class (`SpaceScrollHandler`), own UserDefaults key (`spaceScrollEnabled`). Disabled by default.
- **Dynamic Spaces** → While Mission Control is open, keeps one empty desktop per Spaces bar and removes other empty desktops. An empty active desktop is the spare, even if an occupied or full-screen Space follows it. Otherwise the spare is on the right. Full-screen and Split View Spaces are preserved. Minimized windows count as occupants. Configured in Desktop → Spaces with `dynamicSpacesEnabled`. Disabled by default.
- **Space Indicator** → GNOME's workspace switcher popup: a pill of dots, one per space, the current one filled in, on the display that changed. Driven by the space change itself rather than by any one way of causing it, so it shows for the keyboard shortcut, Mission Control, a swipe, or scrolling the Apple menu alike. Scrolling past either end of the row is the one case with no space change behind it, and `SpaceScrollHandler` reports that separately so the popup still appears. Own watcher class (`SpaceChangeWatcher`), own UserDefaults key (`spaceIndicatorEnabled`). Disabled by default.
- **Dark Menu Bar** → When a window fills the screen, shows a black bar behind the transparent menu bar to make it opaque. Hidden while a window is in full screen, since the window owns the menu bar strip there. Also hidden on a display whose menu bar is drawing dark text, which is what it does over a light wallpaper — the bar cannot change that colour, and dark text on black cannot be read. Disabled by default. Auto-disabled if macOS "Show menu bar background" system setting is on (`SLSMenuBarUseBlurredAppearance`, observed with KVO since System Settings writes it out of process and `didChangeNotification` sees only this process's own writes). Repositions on screen parameter changes.
- **Excluded Apps** → A list of apps SuperOpt stays out of. While one of them is the active app every feature is off and the menu bar icon dims to 50%, so that app behaves as it would with SuperOpt not running. Own class (`ExcludedApps`), own UserDefaults keys (`excludedAppsEnabled` for the toggle, `excludedAppIDs` for the list). Disabled by default.
- All features can be individually toggled on/off in the settings window (persisted via UserDefaults; the defaults match each feature's note above)
- **Every new feature must have a toggle** in the settings window, persisted via UserDefaults. Invasive features, including those that change the user’s desktop layout, are off by default. Other new features are enabled by default.
- **Request Permissions** menu item — checks Accessibility (`AXIsProcessTrusted`) and Input Monitoring (event tap exists), offers buttons to open each settings pane directly
- Option key detection happens on key-up so existing keyboard shortcuts are unaffected

## Architecture

Single-target Swift app compiled with `swiftc` (no Xcode project, no SPM). All sources are in `Sources/`.

| File | Purpose |
|---|---|
| `main.swift` | Entry point — creates NSApplication, sets `.accessory` policy, runs the app |
| `AppDelegate.swift` | Status bar menu, CGEventTap setup, event routing, action triggers (Mission Control / Spotlight). Contains the free `eventTapCallback` function (required for C interop). Menu contains Settings/Permissions/About/Quit plus an Open at Login item whose checkmark `menuNeedsUpdate` refreshes from `SMAppService` on each open — feature toggles are in the settings window. |
| `SettingsWindow.swift` | A non-resizable titled `NSWindow` (`toolbarStyle = .preference`) whose `contentViewController` is an `NSTabViewController` with `tabStyle = .toolbar` — the same AppKit substrate the SwiftUI `Settings` scene builds on. One `NSHostingController` per pane (`sizingOptions = [.preferredContentSize]`), one SF Symbol toolbar item per pane, window title = selected pane. The tab controller does all the sizing itself (see the sizing bullet in Key Implementation Details): the window has **no maximum height** (HIG: "a settings window accommodates the size of the current pane") and every pane is 560 pt wide. `SettingsWindowController` is an `NSWindowController` that builds the window on first use and keeps it; the selected pane persists in `settingsSelectedPane`. |
| `SettingsPanes.swift` | Three of the four settings panes: `DesktopPane` (Mission Control / Spaces / Windows / Menu Bar), `KeyboardPane` (key behaviors — Caps Lock indicator, Home/End, Menu key — plus the Linux shortcut remapping section and its tree; shortcut remapping lives here, not its own pane, because the HIG has each pane hold "a group of related settings"), and `InputPane` (Option Key / Mouse / Finder). Each a SwiftUI `Form` with `.formStyle(.grouped)`. |
| `ShortcutOutline.swift` | The Keyboard pane's shortcut tree plus its bridging `NSViewRepresentable`: `ShortcutNode` (the tree's node class — a class, not a struct, because NSOutlineView identifies items by identity and struct copies defeat `row(forItem:)`) and `ShortcutOutline`, which bridges an NSOutlineView: 24 pt rows with `usesAlternatingRowBackgroundColors`, disclosure triangles, 13 pt-per-level indentation, view-based rows (checkbox + label + trailing key combos), native mixed-state category checkboxes. **Row spacing**: from the outline's leading edge, the disclosure triangle sits at 1 pt, the row's checkbox at 26 pt at the top level and 39 pt one level in, and the label 15 pt past the checkbox's trailing edge. Three things produce that and all three matter: `style = .plain` (the default `.automatic` resolves a point tighter here), the checkbox pinned flush to the cell's `leadingAnchor` (no inset), and a 17 pt label constant — Auto Layout measures from the checkbox's alignment rect, which is 2 pt narrower than its frame, so 17 lands the label 15 pt from the frame. Rows are `NSTableCellView` subclasses laid out with leading/trailing anchors, so they mirror in a right-to-left localization and the label inverts with a selected row via the cell view's `backgroundStyle` forwarding to `textField`. A clicked checkbox is mapped back to its node with `NSTableView.row(for:)` + `item(atRow:)`, and a shortcut's category with `NSOutlineView.parent(forItem:)`, so no state is stored on the button. The row refresh after a checkbox toggle reconfigures the row view through `rowView(atRow:)` because `reloadItem` never re-asks the delegate for a visible row's view. The trailing key-combo field is sized 4 pt wider than its intrinsic size (symbol-heavy strings like ⌘/▸ render a pixel or two wider than they measure and clip at exact size) and inset 14 pt so it clears the overlay scroller that floats over the row's trailing edge while scrolling. |
| `PermissionHelper.swift` | Handles first-launch and menu-triggered permission dialogs. Loops with Continue/Open Accessibility/Open Input Monitoring/Quit. The startup alert checks trust and the event tap when the Accessibility notification arrives, with one modal-mode retry after a failed check. Repositions to top-right to avoid overlapping the system accessibility prompt. |
| `OptionKeyHandler.swift` | Tracks Option key state via `flagsChanged` events. Detects clean single/double presses using a timer. Exposes `onSinglePress` / `onDoublePress` closures. `resync()` adopts the live modifier state after the event tap has been down, so a release the tap never sees cannot fire as a clean press on the next modifier-less `flagsChanged` — the same rule the Caps Lock latch's resync follows. |
| `HotCorner.swift` | Monitors `mouseMoved` events and detects when cursor hits the top-left corner (2px zone) of any screen. Exposes `onTrigger(NSScreen)` closure. Handles CGEvent↔NSScreen coordinate conversion. |
| `RippleAnimation.swift` | Ported from GNOME Shell `js/ui/ripples.js`. Three concentric quarter-circle CAShapeLayer ripples with staggered scale/opacity animations. Displays in a borderless transparent window that orders out when the Core Animation transaction completes, with a dispatch backstop at maxDuration + 0.1 — CATransaction completions measured delivered in every testable configuration, but a display rearrangement mid-animation is the one case that cannot be tested, and it is the condition under which this app's NSAnimationContext completions were measured as never delivered (OSDPanel). |
| `DockLauncher.swift` | Reads persistent dock apps from `com.apple.dock.plist`. Finder is hardcoded at position 1. Launches apps via `NSWorkspace`. Handles Opt+1–9 keyDown events with virtual key code mapping and Finder position adjustment. |
| `MenuKeyHandler.swift` | Opens a context menu when the PC Menu key (0x6E) is pressed with no modifiers. Right-clicks at the caret (located via `kAXBoundsForRangeParameterizedAttribute`) when one is available, else `kAXShowMenuAction`, else the mouse position. Own UserDefaults key (`menuKeyRightClickEnabled`). |
| `LockKeyOSD.swift` | Caps Lock on-screen display, laid out like gnome-shell's OSD window: the ⇪ glyph as a 32pt slot icon beside a bold heading label, in an `OSDPanel`. The glyph is drawn live with Core Text, ink-centered within its view, and dims to 35% when Caps Lock goes off (the opacity of the extension's `capslock-disabled-symbolic`); the label stays full. Pill height/padding from the shared `OSDMetrics`. The label's `baseWritingDirection` is taken from `NSParagraphStyle.defaultWritingDirection(forLanguage:)` on the running localization, because the Latin `⇪ Caps Lock` prefix would otherwise make the first-strong-character heuristic read an Arabic status word before the key name. Both the icon and the label are placed by their **ink**, not their frames: an `NSTextField` cell draws its text ~5pt inside its frame's left edge and its ink center ~1pt below the frame center, so laying the label out by frame left it low beside the ink-centered icon and widened the icon-to-text gap by the cell's left inset. The icon's view is then **raised** so the glyph's visual mass sits on the text's: the glyph is bottom-heavy (a hollow arrowhead over a solid box — its alpha-weighted centroid lands ~1pt below its ink-box center) while the text's mass sits at or slightly above its box center, so centering both bounding boxes left the glyph reading shifted down next to the text. Both offsets are measured at launch (`prepare(texts:)`, called from `applicationDidFinishLaunching` before the event tap exists) by rasterizing through an offline `cacheDisplay` context and scanning the pixels; the event tap path only ever reads the cache or falls back to frame-sized geometry, drawing nothing. |
| `OSDPanel.swift` | Shared on-screen display: a glass pill above the bottom of each given screen, fading in, holding, and fading out. Owns the windows and the timing and takes a closure to fill the pill, so each OSD only has to supply its contents, size, screens, and durations. Windows are kept while the panel is up, so a second `show` updates in place rather than restarting the fade. The fade does not trust the `NSAnimationContext` animation to finish: a delayed block lands the value directly if the animation has not (measured after one display rearrangement: animator alpha changes never progressed, in this app and in a bare probe alike, while direct alpha sets worked) and is the **sole deliverer of the completion** — a completion handed to the animation group is retained forever by a group that never finishes, holding the window with it — and a per-window generation counter retires a delayed block whose fade a re-show or dismissal has superseded. Used by `LockKeyOSD` and `SpaceSwitcherOSD`. Also holds `OSDMetrics` — the shared slot/padding/fade metrics that keep the OSD pills the same general size and fade. |
| `ExcludedApps.swift` | The apps SuperOpt stays out of. Takes the active app from `NSWorkspace.didActivateApplicationNotification`'s `userInfo` once per activation rather than querying it per event, and publishes `isSuspended` plus an `onChange` for the transitions. Own UserDefaults keys (`excludedAppsEnabled`, `excludedAppIDs`). |
| `ExcludedAppsSettings.swift` | The settings pane for the excluded apps (`ExcludedAppsPane`), plus the model behind it: resolves a bundle identifier to an icon and a localized name, adds apps from an `NSOpenPanel` — one defaults write for the whole selection, since each per-app write would fire the KVO observer and a `didChangeNotification`, restarting the watchers behind `defaultsChanged` once per app — and removes the selected rows. The model observes `excludedAppIDs` with the same selector-based KVO `GnomeShortcutSettings` uses — the only route that sees an out-of-process write — and the pane derives its selection through the list, so an app leaving it drops its selection; enforcement still catches up at the next app switch, which `ExcludedApps`' activation observer supplies. The apps are Form section rows (tap to select, accent-tinted row) with the +/− pair in a plain row below. The +/− pair is an `NSSegmentedControl` (via `AddRemoveSegment`, an `NSViewRepresentable`) — two 24 pt segments with `plus`/`minus` symbol images (**not** `NSImage(named: NSImage.addTemplateName)` — the named lookup returns a process-wide cached instance, so setting an accessibility description on it renames the template for every other use of it in the process) in a 49×24 pt rounded control, the remove segment disabled with nothing selected, left-aligned under the list. macOS 26/27 `.formStyle(.grouped)` caveats learned while trying (and reverting) an edge-to-edge footer strip: `listRowBackground` is ignored (the Form is not List-backed), `.background` on row-root content renders behind the row's opaque material, and row content is inset 10 pt. A fixed frame wider than the row's content area overflows the Form's ideal size, so keep row content flexible. |
| `SpaceSwitcher.swift` | Reads which space each display shows, through SkyLight — read only. `displays()` returns each display's space list and current index in strip order, and `target(for:)` resolves a screen to the spaces its Apple menu controls plus the screens that move with them. |
| `SpaceShortcut.swift` | Reads the system's "Move left/right a space" shortcut out of `com.apple.symbolichotkeys` (IDs 79 and 81, honouring a rebound key and the enabled flag, defaulting to ⌃← / ⌃→ when the preference holds no entry) and posts it. |
| `SpaceScrollHandler.swift` | Turns a scroll over the Apple menu into a space switch. Gates on cheap geometry first, then on the Apple menu's own frame; a display without a menu bar ("Displays have separate Spaces" off, non-main displays) is not a candidate, since its top strip is ordinary screen space. Accumulates travel so one gesture is one space, with the travel bound to one display — a gesture begun on one display's Apple menu does not carry to another's. Reports only the end-of-row case through `onEdge`, since every other scroll produces a real space change for `SpaceChangeWatcher` to notice. Own UserDefaults key (`spaceScrollEnabled`). |
| `DynamicSpacesHandler.swift` | Reconciles desktop occupancy against WindowManager’s live Mission Control controls. On macOS 27 its AX application has one `mc.display` child per display, identified by `AXDisplayID`. Under `mc.spaces`, `mc.spaces.add` supports `AXPress` and removable buttons in `mc.spaces.list` support `AXRemoveDesktop`. The planner keeps the active desktop when it is empty. A removal re-checks occupancy, and both actions confirm the current index and Space order just before pressing the button. WindowManager itself puts a layer-zero window on empty inactive desktops during Mission Control. Exclude its PID when counting windows. |
| `SpaceChangeWatcher.swift` | Notices a space change however it was made, by observing `NSWorkspace.activeSpaceDidChangeNotification` and comparing each display's current space with the last reading. A display seen for the first time — connected after `start()`, missed by the transient read there, or reconnected after an absence dropped its baseline — is recorded without firing; its first reading is not a change. An absence is only observed when a space change happens without the display, so one that leaves and returns entirely between notifications keeps its baseline — an accepted residual, since a reconfiguration that changes a display's space without any notification is not known to occur. An empty display list is a failed WindowServer read, not a reading, so it touches no baselines. Fires `onChange` with the display and the screens showing it. ## Build & Install

```bash
./build.sh        # compiles Sources/*.swift → build/SuperOpt.app
make install      # moves to /Applications (builds first if needed)
make run          # kill → clean → install → open: the way to run a change
```

**To run a change, use `make run`** — it replaces the instance already running, so there is only ever one SuperOpt on the machine. Launching a second build out of `build/` or a scratch worktree leaves two SuperOpt processes competing for the same event tap and the same defaults domain, and both answer to the name "SuperOpt", so accessibility and `pgrep` lookups silently measure the wrong one. Use `./build.sh` to check that a change compiles; use `make run` to see it work.

**The bundle identifier is `co.logonoff.superopt`**. It is set in `Info.plist`, and it is the UserDefaults domain every setting named in this document lives in, at `~/Library/Preferences/co.logonoff.superopt.plist` (the Homebrew cask's `zap trash` points at the same path). Inspect or change a setting from the shell with `defaults read co.logonoff.superopt` / `defaults write co.logonoff.superopt <key> …`. Getting the domain wrong is silent: `defaults write` happily creates any arbitrary key and reports success, the app never sees the value, and the stray plist stays behind.

No Xcode project — just `swiftc` with `-framework Cocoa`. Build script at `build.sh`. The deployment target is set once via `DEPLOYMENT_TARGET` in `build.sh` and must stay in sync with `LSMinimumSystemVersion` in `Info.plist`. **`swiftc` must be passed an explicit `-target`** — left to its own defaults it stamps a `minos` newer than the running OS (`minos 28.0` on macOS 27), and LaunchServices then refuses to launch the app with `kLSIncompatibleSystemVersionErr` (-10825). `MACOSX_DEPLOYMENT_TARGET` is ignored by `swiftc`, so it can't be used instead. Check with `vtool -show-build-version build/SuperOpt.app/Contents/MacOS/SuperOpt`, which reports both `minos` and the SDK the binary was linked against. **The SDK must be at least as new as `DEPLOYMENT_TARGET`**: macOS gates behaviour changes on the linked SDK, not on the deployment target, so an older SDK silently produces a build that behaves unlike the release — on macOS 27 that includes `NSMenu` auto-hiding menu item images and `NSTextView.menuForEvent:` moving Layout Orientation into the Font submenu. `build.sh` enforces this: it honours an explicit `DEVELOPER_DIR`, otherwise selects the newest installed **Xcode** carrying a new enough SDK, and otherwise warns. CI sets `STRICT_SDK=1`, turning that warning into a hard failure so a release is never cut against the wrong SDK. Only full Xcode installs are candidates — the Command Line Tools can ship a newer SDK than the selected Xcode, but provide neither the `sourcekitd` SwiftLint loads nor `actool`. The check treats an unreadable SDK version as a failure rather than a pass, because `xcrun` returns nothing while Xcode is mid-upgrade or its licence is unaccepted. The `minos 28.0` default noted above is itself a symptom of a mismatched toolchain: under Xcode 27, `swiftc` defaults to `macosx27.0.0`. Keep the explicit `-target` regardless, so the stamped `minos` never depends on which Xcode is selected. **Every `dlsym` / private API usage must have a comment (2–3 lines) explaining what the private API does and why no public API can achieve it.** The comment should name the private symbol, describe what it returns or does, and state the specific limitation of public alternatives that makes the private API necessary. **Always use `./build.sh` to compile and verify changes** — never run `swiftc` or `swiftlint` directly, since the build script also handles linting, localization validation, icon compilation, code signing, and version stamping. A `Package.swift` exists for IDE support (symbol resolution across files) but is not used for production builds. Version is stamped into `Info.plist` at build time via `git describe --tags --dirty --always`. If `actool` is available (requires full Xcode, not just CLT), the Liquid Glass icon from `Icon.icon` is compiled into `Assets.car` and bundled; otherwise the icon step is skipped. SwiftLint enforces a 400-line file limit; **when a file exceeds this, extract types or extensions into new files** rather than compacting whitespace or merging lines. SwiftLint runs before compilation if installed (`brew install swiftlint`); build fails on any violation. Compiler warnings are also fatal (`-warnings-as-errors`), so a warning must be silenced deliberately — e.g. via a documented availability annotation — rather than lost in build noise. **Every `// swiftlint:disable` comment must have a justification comment explaining why the rule can't be satisfied.** Fix the underlying issue instead of disabling the rule when possible. For `force_cast` on Core Foundation types (`AXUIElement`, `AXValue`), use the `KeyboardUtils.toAXElement`/`toAXValue` helpers instead of inline disables.

## Localization

All user-visible strings are localizable. Non-SwiftUI strings (menu items, alerts, OSD text) use `NSLocalizedString()`. SwiftUI `Text("literal")` strings auto-resolve via `LocalizedStringKey`.

- **Languages**: English (en), Arabic (ar), Chinese Simplified (zh-Hans), French (fr), German (de), Italian (it), Japanese (ja), Korean (ko), Portuguese Brazilian (pt-BR), Russian (ru), Spanish (es)
- **Source strings**: `Locales/en.lproj/Localizable.strings` (UTF-8, checked into repo)
- **Regenerating**: Delete `Locales/en.lproj/` and run `./build.sh` — it runs `genstrings -SwiftUI` and converts from UTF-16 to UTF-8.
- **How genstrings extracts SwiftUI strings**: `genstrings -SwiftUI` picks up `Text("…")` calls with literal string arguments at any closure depth (inside `Toggle { }`, `Picker { } label: { }`, `Section { } header: { }`, and `ForEach`). It does **not** extract string-literal arguments passed directly to SwiftUI initializers (`Section("…")`, `Toggle("…", isOn:)`, `Picker("…")`) nor literals routed through constants (`let k: LocalizedStringKey = "…"` used as `Text(k)`) — and no genstrings flag can change this (`-SwiftUI` only enables the `Text()` initializer; `-s` only matches the `NSLocalizedString("key", comment:)` shape and errors on every SwiftUI form). Therefore: always write user-visible labels as literal `Text("…")` inside a closure (`Section { … } header: { Text("…") }`, `Toggle(isOn:) { Text("…") }`), never as a direct string-literal argument or via an intermediate constant. A string that only appears as a direct initializer label will silently go missing from every locale. `Text("…", comment: "…")` is also extracted — it is how a SwiftUI string carries its translator comment; a `Text()`-less array of `NSLocalizedString`s is never needed as a comment carrier.
- **Adding a language**: Create `Locales/XX.lproj/Localizable.strings` (copy from `Locales/en.lproj/`, translate the right-hand values). The build script copies all `Locales/*.lproj` directories automatically.
- **Adding new strings**: For AppKit code, wrap in `NSLocalizedString("key", comment: "description")`. For SwiftUI, write the label as a literal `Text("…")` per the genstrings rule above. The build script automatically detects missing keys in non-English locale files and adds them with English placeholder values. **After the build, translate the placeholder strings** in all locale files (`ar`, `de`, `es`, `fr`, `it`, `ja`, `ko`, `pt-BR`, `ru`, `zh-Hans`) to the target language. Use Apple's official terminology where applicable (check `support.apple.com` localized pages or system `.strings` files for canonical translations). The build script warns on missing or extra keys. Proper nouns Apple itself keeps in English in most locales (e.g. "Mission Control") are listed in `PROPER_NOUNS` in `build.sh` — their untranslated check passes them through, because the correct localized value equals the English source.
- **Smart quotes in `.strings` values**: curly quotes are safe **inside** values — `plutil` only breaks when they are used *as* the string delimiters (never write `"key" = “value”;`). Locales use Apple's real quote characters for UI-element names, measured against the localized macOS UI itself: `“…”` in zh-Hans, Japanese, Italian and Spanish, `„…“` in German, `«…»` in French and Russian, straight `"…"` in Arabic, `‘…’` in Korean. The English source quotes sentence-style onscreen setting names in curly double quotes (`“Show menu bar background”`).

## Key Implementation Details

- **Battery efficiency**: Prefer event-driven code when system notifications or callbacks can deliver the required behavior reliably and promptly. Use a timer when events alone would miss a change, delay visible feedback, or otherwise reduce product quality. Keep any necessary timer active only as long and as often as the feature requires.
- **The settings window follows the stock-app pattern'**: a non-resizable titled `NSWindow` (titled + closable only — no resize, no miniaturize) with `toolbarStyle = .preference`, whose `contentViewController` is an `NSTabViewController` with `tabStyle = .toolbar` — the same AppKit substrate the SwiftUI `Settings` scene builds on: the tab items become the centered toolbar icons, one per pane. **The window title does not follow the selected child view controller on an already-shown window** — `canPropagagateSelectedChildViewControllerTitle` propagates the child's `title` into the tab controller, but `NSWindow.title` only picks it up when `contentViewController` is assigned, so `tabView(_:didSelect:)` sets `window.title` itself.
- **`NSTabViewController` does the whole job of sizing the settings window — don't help it**: with `sizingOptions = [.preferredContentSize]` each `NSHostingController` reports its form's ideal size, and the tab controller resizes the window to the selected pane *and holds the window's top edge* across switches. There is no `NSWindow` subclass and no frame arithmetic. Measured by building the app with every hand-rolled correction (a `setFrame`/`setContentSize`-overriding `NSWindow`, a `fit()` helper, a `pinnedTop` + `windowDidMove` guard) switched off and driving five pane switches: identical per-pane heights, width constant at 560 pt, and the top edge constant to the point (907.0 on every sample). The only difference is that AppKit's resize lands one layout pass later instead of synchronously. **The earlier "the `.preference` toolbar overhangs the content rect" finding was wrong** — `contentRect(forFrameRect:)` and `contentLayoutRect` measure equal at every sample, with a constant 88 pt chrome, in both a minimal probe and the real app. What looked like a 36 pt shortfall was a frame read before AppKit's first layout pass: assigning `contentViewController` leaves the window at a stale size for one pass (measured: 588 pt for a pane that settles at 301 pt), so anything that measures and sets a frame there fights every correct frame AppKit sets afterwards. The one ordering that does matter: `window.center()` must come after `window.layoutIfNeeded()`, or the window is centered at its placeholder height and then grows downward from that top edge.
- **`NSTabViewController` never animates its window resize, so the app has to**: measured across plain `NSViewController` panes and `NSHostingController` panes, with and without `transitionOptions = [.crossfade]`, with `.preference` and the default toolbar style, and with `.toolbar` and `.segmentedControlOnTop` tab styles. Every one: a single un-animated `setFrame`, ~620 ms after the switch, so the new pane crossfades in at the old pane's height and the window snaps under it. SwiftUI's `Settings` scene is no help either — it caps the window and scrolls a taller pane inside it rather than resizing (measured: constant 450 pt across panes of 3 and 22 rows). `SettingsTabViewController.resize` animates the frame itself with `window.animator().setFrame` in an `NSAnimationContext` group, skipped under Reduce Motion. Three things make it work:
  - **The duration is `NSWindow.animationResizeTime(_:)`**, AppKit's own figure for a frame change of that size — it scales with the distance, caps at 0.350 s, and honours the `NSWindowResizeTime` default. It is what the blocking `setFrame(display:animate:)` uses internally, so the timing matches a window AppKit resizes itself rather than coming from a hand-picked constant.
  - **The resize is set synchronously from `didSelect`, and must be.** Two milliseconds after the switch AppKit's constraint engine sets the window to the new pane's height itself (measured: `setFrame` from `NSWindow(NSConstraintBasedLayoutInternal)` via `NSISEngine`), so anything scheduled even one runloop turn later finds the window already at the target and animates nothing. Setting the frame first leaves the constraint pass with nothing to do. The target is known that early: a pane's `preferredContentSize` is already exact when the switch begins (measured 188 pt and 749 pt against the 276 pt and 837 pt windows AppKit eventually settles on, chrome a constant 88 pt). **This is also why an `AXPress` is not a valid test of the animation** — it, and a deferred resize, both hid the bug while a real mouse click did not; verify pane switches by posting a `CGEvent` click at the toolbar item. Interrupting an animation is safe — each call recomputes from the live frame and holds the top edge, and five switches 120 ms apart settled on the right height with the top edge constant to the point.
  - **The pane is hidden for the resize and revealed at the end, and there is no crossfade** (`transitionOptions = []`). The content area stays blank for the whole resize, with the toolbar selection and window title already switched, and the new pane appears only once the window has stopped moving. It also solves the scroller: a pane whose form is briefly taller than the window shows a scrollbar for the length of the animation otherwise. `didSelect` sets the incoming pane's `view.isHidden`, and every path out of `resize` clears it — including the early returns, or a pane that needs no resize would never come back.
- **A pane that can grow without bound must hold the growth inside itself**, not in the window: the Keyboard pane's shortcut tree is a fixed-height (320 pt) scrolling `NSOutlineView` (see `ShortcutOutline.swift`), so expanding every category leaves the pane at a constant height (measured 871 pt; as plain Form rows it once grew to 2,591 pt).
- **A SwiftUI `List` nested in a `Form` never receives scroll gestures, and one below a Form loses its row backgrounds**: the Shortcut Remapping tree went through both — a `List` of `DisclosureGroup`s inside a Form section rendered but would not scroll, and a standalone `List(children:)` (which is NSOutlineView-backed, with native triangles and indentation) scrolled but drew its `alternatesRowBackgrounds` stripes in multi-row blocks no matter what `listRowBackground` combination was set (verified against minimal probe windows: the same code stripes perfectly when nothing sits above the list, and stops as soon as a Form or even a lone Toggle precedes it). The reliable answer was to bridge `NSOutlineView` directly (`ShortcutOutline.swift`), which also bought native mixed-state checkboxes and per-level indentation. **That finding is about SwiftUI's `List`, not about nesting a scroll view in a Form**: the bridged `NSScrollView` lives in a `Section` of the Keyboard pane's Form and scrolls normally — a hit test at its centre returns the `NSOutlineView`, and the first `NSScrollView` up that responder chain is the tree's own, not the Form's (measured), and a posted scroll wheel over it moves the tree. Two AppKit behaviors found on the way: `reloadItem` does not re-ask the delegate for a visible row's view, so the post-toggle refresh reconfigures the row view via `rowView(atRow:)`; and outline items must be a class — struct copies defeat `row(forItem:)`, so the refresh silently no-ops (measured: every checkbox press showed only the button's own off → mixed → on cycling until the nodes became class instances).
- **Every pane shares one width** (`settingsPaneWidth`, 560 pt) so switching panes never moves the window sideways, and the window is not resizable, so `NSWindow`/SwiftUI min-max size fights do not arise.
- **An accessory app's windows cannot come to the front via the cooperative `activate()`**: `NSApplication.activate()` (macOS 14+) is documented as not guaranteeing activation, and it measurably never activates SuperOpt while another app is frontmost — `makeKeyAndOrderFront` then orders the settings window *behind* the active app's windows, because a non-active app's windows cannot rise above the active app's. Verified with a probe replicating `SettingsWindowController.show()` verbatim against a frontmost Firefox: plain `activate()` left `isActive == false` and the window behind; `activate(ignoringOtherApps: true)` fronts it and makes it key. That variant is deprecated since macOS 14 but still works on macOS 27 and is the standard menu-bar-app pattern — the cooperative replacement has no way for the *other* app to `yieldActivation`, so it is unusable from a status-item action. Raising on open is also what the HIG expects: the window a person just opened is the key window that accepts input. `SettingsWindowController.activateAndFront` and `showAbout` both use it.
- **Event tap**: Active tap (`CGEventTapOptions.defaultTap`) on `cgSessionEventTap`. Monitors: `flagsChanged`, `keyDown`, mouse down events, `mouseMoved`. A disabled tap (`tapDisabledByTimeout`/`tapDisabledByUserInput`) is routed through `accessibilityChanged`, which re-enables it, verifies the re-enable, and tears it down for a fresh rebuild when it will not come back. Only Opt+N keyDown events are consumed; all other events pass through unchanged.
- **Dock shortcuts**: Reads `~/Library/Preferences/com.apple.dock.plist` → `persistent-apps` array. Finder is always position 1. Virtual key codes 0x12–0x19 map to number keys 1–9.
- **Option key "clean press"**: A press is dirty (ignored) if any other key, mouse button, or modifier is used while Option is held. This prevents triggering on Opt+Tab, Cmd+Opt, Opt+Click, etc.
- **Double press timing**: 300ms threshold between two clean Option releases. Any further release within the threshold after the last one is the tail of the same burst and is ignored, so a rapid burst of any length fires only the double-press action.
- **Don't call these keys F3/F4**: the top-row keys that trigger Mission Control, Spotlight and Apps are dedicated feature keys with their own virtual key codes (160, 131, 177), always carrying `maskSecondaryFn`. The real function keys are different codes entirely — F3 is 99, F4 is 118 — so "F3" names the wrong key, not merely the same key loosely. Which F-position a given feature shares is also per-model: Apple's ["How to use the function keys on your Mac"](https://support.apple.com/en-us/102439) states outright that "Not all keyboards have symbols for the same functions", and the F-numbers it shows are one example layout. Apple's collective term for the row is **function keys**, and it does not give the individual keys proper names — it names the feature each symbol controls ("symbols for controlling display brightness, Mission Control, Spotlight, and Dictation"). "The Mission Control key" / "the Spotlight key" / "the Apps key" follow that framing and are what this codebase uses.
- **Spotlight trigger**: Emulates the Apps key (which previously opened Launchpad) by posting key code `131` with `.maskSecondaryFn` via `KeyboardUtils.postKey`. The Fn flag is required — key code 131 without it does nothing. macOS routes this key to the Spotlight Apps view now that Launchpad is gone, so this toggles the panel exactly like the hardware key does. The old `spotlight://apps` URL no longer works on macOS 27: the Spotlight UI moved into `/System/Applications/Siri AI.app` (`com.apple.campo`) and its `spotlight:` LaunchServices claim is flagged `apple-internal`, so `NSWorkspace.open(_:)` fails with `kLSApplicationNotFoundErr` ("no application set to open the URL"). Opening the URL with `open(_:withApplicationAt:)` against `com.apple.campo` also works, but depends on both the private URL scheme and the bundle ID, so key emulation is preferred.
- **Feature keys are not `systemDefined` events**: The dedicated feature keys in the top row emit ordinary `keyDown`/`keyUp` events with `maskSecondaryFn`, visible at both the HID and session taps — not `NX_SUBTYPE_AUX_CONTROL_BUTTONS` events. The Apps key emits key code `131`, the Mission Control key emits key code `160`, and the Spotlight key emits key code `177`. Synthesizing `NX_KEYTYPE_LAUNCH_PANEL` (13) as a `systemDefined` event is correctly formed and reaches the session tap, but macOS ignores it. Verify what a special key actually emits with a listen-only tap before trying to synthesize it.
- **Mission Control trigger**: Emulates the Mission Control key by posting key code `160` with `.maskSecondaryFn` via `KeyboardUtils.postKey`. As with the Apps key, the Fn flag is required and the key toggles, so triggering it again closes Mission Control. Replaces spawning `/usr/bin/open -a "Mission Control"`, which still works but costs a subprocess.
- **Hot corner detection**: Uses velocity-based triggering inspired by GNOME's `PressureBarrier`. GNOME accumulates cursor pressure (100px threshold in a 1000ms window) against pointer barriers. Since macOS pointer barriers are private API, we approximate by measuring cursor speed — only triggers when the cursor enters the 2px corner zone at ≥500 pts/sec, filtering out slow drifts. Resets when cursor leaves the zone.
- **Hot corner coordinate math**: CGEvent uses flipped coordinates (0,0 = top-left of primary display). NSScreen uses bottom-left origin. Conversion via `KeyboardUtils.cgRectToNS`.
- **Dock auto-hide and window sizing**: `NSScreen.visibleFrame` excludes the Dock and menu bar. When "Automatically show and hide the Dock" is off, `visibleFrame` is shorter/narrower than `frame`. Tiled and filled windows match `visibleFrame`, but may extend slightly past it. Window-size checks (Tile Assist detection, MenuBarBackground fill detection, ZoomButtonHandler fill detection) must use `<=`/`>=` with tolerance rather than `abs()` equality, so windows that extend into the Dock area still match.
- **Check `kAXEnabledAttribute` before pressing a menu item**: pressing a greyed-out item does nothing, so a handler that reports success consumes a keystroke or click for no reason. Measured on TextEdit's Window menu — windowed: Fill 1, Left 1, Return to Previous Size **0**; full screen: all three **0**. Those zeroes were two live bugs: ⌥↓ was swallowed on every window that had never been tiled (the normal state of any window), and all four Option+Arrow keys were swallowed in full screen, which is where ⌥←/→ word navigation matters most. The attribute is accurate without opening the menu first, so it can be read inline on the event tap.
- **Post synthetic clicks with an explicit event source and cleared flags**: `CGEvent(mouseEventSource: nil, …)` inherits the current modifier state, and a test harness that posts Option+key events without a matching `flagsChanged` leaves Option stuck on. The resulting clicks arrive as ⌥-clicks: `ZoomButtonHandler` ignores them by design, macOS does its own ⌥-zoom, and the feature looks broken when it isn't. Set `flags = []` on synthesized mouse events before posting.
- **Reading spaces is SkyLight-only; changing them has to go through the system's shortcut**: there is no public API for spaces at all — AppKit lets a window say which spaces it joins and stops there. `SLSCopyManagedDisplaySpaces` reads them, per display: entries carrying a `Display Identifier` (the display's UUID, matching `CGDisplayCreateUUIDFromDisplayID`), a `Spaces` array in strip order left to right, and a `Current Space`, each with an `id64`. Entries exist for displays that are remembered but not connected, so resolve by UUID rather than by position in the array. When displays share spaces the list collapses to a single entry whose identifier matches no screen, which is the signal that every display moves together.
- **Don't switch spaces with `SLSManagedDisplaySetCurrentSpace`**: it moves the space and animates, so it looks right, but it only updates the bookkeeping. The menu bar is left drawing the outgoing space's app over the incoming one's — two apps' menus interleaved — and it stays that way: it survives moving the pointer away, activating the frontmost app, and further switches by the same call. Only a real space switch repairs it. Reproduced from a clean boot, from a command-line tool as well as from SuperOpt, so it is the call itself and not the caller or the pointer being over the menu bar.
- **Posting the space shortcut acts on the display under the pointer**: which is exactly what scrolling a display's Apple menu wants, and needs no focus juggling. Verified both ways round — with the focused app on one display and the pointer on another, the display that moved was the pointer's. The shortcut lives in `com.apple.symbolichotkeys` under ID 79 (left) and 81 (right); `parameters` is `[character, keycode, modifiers]`, where the modifier mask uses the same bit values as `CGEventFlags`, including `0x800000` for the function bit that arrow keys carry. An absent entry means the user never changed it, so the default ⌃← / ⌃→ applies; `enabled = false` means the user turned it off, and then nothing can switch spaces by key. **A synthesized key does trigger it** — ⌃↑ opened Mission Control in the same way — so an earlier conclusion that synthetic keys cannot drive space switching was wrong: those tests were pressing against the end of the row, where the shortcut correctly does nothing.
- **A window shown during a space switch is dragged away by it**: the window server composites every window on the display into the transition, panels included. Measured on a 2560-wide display, an OSD put up as the switch began slid from x=820 to x=2736 over about a second and only reached its intended position as the animation ended — most of the 600 ms it was supposed to be readable. `.screenSaver` level does not exempt it, and neither does `canJoinAllSpaces`.
- **A wheel notch is not a distance**: `scrollWheelEventIsContinuous` tells a wheel (0) from a trackpad (1), and the two have to be read differently. A wheel's point delta carries the system's scroll acceleration — about 10pt for an unhurried notch, more when spun — so a distance threshold makes a slow wheel feel like it needs several notches to do anything, which is what a 40pt threshold did: four. Count notches for a wheel, accumulate points for a trackpad.
- **macOS ignores a space-switch shortcut while a switch is animating**: measured by posting right then left 120 ms apart, which ended one space to the right rather than back where it started. So extra notches during the animation cost nothing and need no rate limiting of our own — the system absorbs them.
- **`NSWorkspace.activeSpaceDidChangeNotification` arrives when the animation ends**, which is both the moment a panel can be shown without being dragged and the moment the space list reads correctly. Measured about 1.2 s after the keystroke that caused the switch, with `SLSCopyManagedDisplaySpaces` already reporting the new space at that point — a read taken 1.0 s after the keystroke still returned the old one, which is the animation not having finished rather than this process seeing stale data. The notification says nothing about which display moved, so `SpaceChangeWatcher` keeps the last current space per display and compares. It needs a real app to arrive: a plain command-line tool with a run loop never received it, the same code under `NSApplication` with `.accessory` policy did.
- **`AXUIElementCopyElementAtPosition` sees SuperOpt's own overlays**: hit-testing the Apple menu returned the dark menu bar window instead, because that overlay covers the whole strip and the hit test answers with the topmost element — `ignoresMouseEvents` keeps it out of event routing but not out of accessibility. Read the element's frame from its owner instead: `SpaceScrollHandler` asks the frontmost app's `AXMenuBar` for its first child, which is the Apple menu in any language, and compares frames. The frame also carries across displays, since every menu bar puts the Apple menu the same distance from the top-left corner.
- **Scroll direction is left as the system reports it**: natural scrolling flips the sign before the event reaches the tap, and `NSEvent.isDirectionInvertedFromDevice` is not set on injected events, so it cannot be used to normalise one in a test. Nothing is normalised: scrolling up goes to the space on the left and down to the right, which follows whichever way the user has set scroll direction, same as GNOME. Note when testing that the system applies that flip to synthesized scroll events too — a posted `wheel1` of -12 arrives at the tap as +24.
- **A full-screen window is identified by the undocumented `AXFullScreen` attribute**: it reads 1 on a window element occupying a full-screen space and 0 otherwise. There is no public constant for it (`AXAttributeConstants.h` has `kAXFullScreenButtonAttribute`, not `kAXFullScreen`), and no public API reports another app's full-screen state. The traffic light subrole is not a substitute: the green button reports `AXFullScreenButton` windowed and flips to `AXZoomButton` in full screen, which is also what an older non-full-screen-capable window reports. The buttons sit at a negative y while the title bar is auto-hidden, and move on screen when it reveals.
- **A full-screen window's height depends on a system setting, not on full screen itself**: System Settings → Control Centre → "Always show menu bar in full screen" (`AppleMenuBarVisibleInFullscreen` in `NSGlobalDomain`) decides whether the window gets the whole display. With it **off** (the default), the menu bar auto-hides and the window covers `screen.frame` — measured `0,0 1920x1080` on a 1080p display, so the window owns the menu bar strip and anything drawn there covers app content. With it **on**, the window stops at the menu bar — measured `0,30 1920x1050` — which is byte-identical to an ordinary filled window, so geometry alone cannot tell the two apart. `NSScreen.visibleFrame` keeps the menu bar inset in both cases, and `NSScreen.screens` reports only the display holding the active full-screen space when "Displays have separate Spaces" is off. **Test full-screen behavior with the setting off**, or the case that matters never occurs.
- **Turning every feature off at once goes through `isEnabled`**: `AppDelegate.isEnabled` answers false for every key while the active app is excluded, which both skips the handlers on the event tap and — because `defaultsChanged()` runs on each transition — stops the timers and observers behind Tile Assist, the space indicator and Mission Control. A handler that reads its own setting instead of going through `isEnabled` (`FinderCutHandler`, `MissionControlSearchHandler`, `ScrollZoomHandler`) would not be covered, so `handleEvent` also returns early. That early return blocks only *new* events, not a feature's own in-flight work: a pending type-to-search session is abandoned by `mcSearchHandler.reset()` from `applyExclusion` on the way into an excluded app, and a Tile Assist arrange press still waiting on its app to activate is abandoned by `SnapAssistPanel.cancelPendingTileActions()` from the same `defaultsChanged` branch — the same category of in-flight synthetic input as the middle-click paste (the click-through replay is the one deliberate exception — its press is the user's own click being restored). Anything already on screen, such as the Tile Assist panel, is dismissed there too.
- **Read the active app on activation, not per event**: the tap sees a `mouseMoved` for every pointer position, and `NSWorkspace.frontmostApplication` is not free. `ExcludedApps` caches the answer and refreshes it on `NSWorkspace.didActivateApplicationNotification`, so the per-event cost is a `Bool` read. It also refreshes from `defaultsChanged()`, for a list edited while the app it names is active.
- **`frontmostApplication` answers with the outgoing app inside the activation notification**: so anything keyed off it from that notification runs one app switch behind. With Calculator excluded, that inverted the whole feature — every feature on in Calculator and off everywhere else. Measured in SuperOpt: the notification says `com.apple.calculator` while the query says `com.apple.finder`, on every switch, and it persists rather than settling. It does **not** reproduce in a standalone tool, whether another process activates the app or the observing process does it itself, so the probe to write is one that goes through the real path. Click-through focus is what exposed it, because that is what activates apps from inside SuperOpt while a press is withheld at the tap. Take the app from `userInfo[NSWorkspace.applicationUserInfoKey]` instead, and keep `frontmostApplication` only for the initial reading.
- **A click-through press in flight has to be replayed even as the feature is being turned off**: clicking into an excluded app suspends SuperOpt part-way through the withhold-focus-replay sequence, and resetting the handler there swallows the click that brought the app forward. `defaultsChanged` therefore reads `clickThroughFocusEnabled` straight from `UserDefaults` rather than through `isEnabled`. The replay itself is fine while suspended: it is tagged synthetic and reaches the window. The release is routed to the handler ahead of the suspension guard while a press is in flight (`hasPendingPress`): activation can take longer than the click, and without the routing the release is never recorded (or consumed after the replay), leaving the window with the button down and a stale `.replayed` injecting a phantom up later. A new press while suspended supersedes the in-flight one (`handleSuspendedInput` resets the handler), so the excluded app's own clicks pass through untouched rather than being consumed by leftover state. `dropWithheldPress` preserves a `.replayed` obligation across the feature turning off, for the same reason — the press is already on its way to the window, and its release still has to be re-ordered behind it.
- **A SwiftUI `Form` only builds the rows on screen**: a section scrolled out of view is absent from the accessibility tree entirely, so a script that reads the settings window sees whatever is visible and nothing else. Scroll the window first, or check the section headings (`AXHeading` elements), which are present for the whole form.
- **Nothing an app draws changes the colour of the menu bar's text**: the system picks it from what it finds behind the menu bar — the wallpaper, or the background it puts up itself for a window it considers to fill the display — and a bar drawn in the strip is not part of that. Measured with a black bar at window levels 0, 3, 23 and `kCGBackstopMenuLevel`: the text stayed dark over a light wallpaper in every one. The two desktop levels are worse than useless, as the bar renders behind the wallpaper and never appears. So over a light wallpaper a black bar leaves black text on black, and the only fix is not to draw it.
- **A status item carries the appearance of the menu bar it sits in**: `NSStatusItem.button.effectiveAppearance` is `NSAppearanceNameVibrantLight` when that menu bar draws dark text and `VibrantDark` when it draws light text. It follows the menu bar, not the system: in Dark Mode over a light wallpaper it reads vibrant light. That is the signal `MenuBarBackground` uses, and it needs no Screen Recording permission, unlike sampling the screen. Drawing the bar does not change it, so there is no feedback loop — measured stable over four seconds of 0.5 s ticks.
- **The menu bar's appearance is per display, and only the active one can be read**: the status item sits in one menu bar at a time, and `NSScreen.main` names that display, so the pair gives a per-display reading of whichever display is in use. Measured on three displays sharing one wallpaper file: the crops differ enough that one reads vibrant light while another reads vibrant dark, so a single global answer is wrong for a real setup. `MenuBarBackground` keeps the last reading per display ID. A display with no reading of its own goes by the others: where every reading says light text the wallpaper is dark all round and the bar is safe, and one light menu bar anywhere is enough to leave an unread display alone until it has been read. Without that, a second display never got the bar until it had been clicked into once. SkyLight has no C function for this: `SLSGetMenuAppearanceThemeOnSpace` returns the system Dark Mode theme (1 on every display while their menu bars differed), `SLSGetMenuBarDrawingStyle` and `SLSGetActiveMenuBarDrawingStyle` both return 0, and the per-display `appearance` in SkyLight's own `SLSMenuBarAgentManager.MenuBarMetrics` is Swift-internal. `NSWorkspace.desktopImageURL(for:)` is no substitute either: it returned the same dynamic `DefaultDesktop.heic` for all three displays, `NSImage` reads its first frame rather than the one on screen, and it went on naming that file after the wallpaper had been changed to a solid colour — it does not track changes at all. What does is the modification date of `~/Library/Application Support/com.apple.wallpaper/Store/Index.plist`, which moved the moment the wallpaper was set; `MenuBarBackground` watches it and drops its readings when it changes, since a reading is only good for the wallpaper it was taken against. The display in use is read again twice a second regardless, so only the others can go stale.
- **A status item's window stays on the primary display**: `NSStatusItem.button.window.screen` is therefore not a way to tell which display's menu bar the item is being shown in — measured constant at the primary while the item's appearance tracked the active display. `NSScreen.main` is the one that follows, including when the focused window is dragged to another display, and it agrees with SkyLight's `SLSCopyActiveMenuBarDisplayIdentifier` in every sample, so there is no reason to reach for the private call.
- **macOS puts up its own menu bar background for a window it considers to fill the display, and that turns the text white**: which is why the bar looks right in that case — black bar, white text. It is not a pure function of geometry. A window 4 pt wider than the display did not get it; the Fill menu item, which only trimmed that overhang, did; and setting the same filled frame back through the accessibility API afterwards did not bring it back. So the feature's own fill test cannot be made to agree with it, and the text colour has to be read instead.
- **Ripple animation**: Uses GNOME's exact parameters — three ripples with delays 0/50/350ms, durations 830/1000/1000ms, scale easeOut, opacity easeIn. Quarter-circle shape via CGPath arc.
- **A dispatch signal source must be retained, and should not use the main queue**: `DispatchSource.makeSignalSource` returns an object nothing else retains — a source held only in a local is released at scope exit, its registrations die with it, and with `signal(SIGTERM, SIG_IGN)` already set the signal is then ignored for the process lifetime (measured: the process survives `kill -TERM` outright). The main dispatch queue keeps draining during a modal entered from a plain AppKit callout (measured: a `.main` source fires under the permission dialog), but starves when the modal — or anything else — is entered from inside a main-queue block, because the drain is non-reentrant and the blocked block is the queue's own; a private serial queue fires in every configuration, which is why the SIGTERM source uses one. (`PermissionHelper` receives distributed notifications in the startup alert's modal run loop when launched from the AppKit delegate callback. A probe on macOS 27.2.1 found that delivery stalls when the alert is entered from a main-queue block.)
- **Permissions**: Requires both **Accessibility** and **Input Monitoring** in System Settings → Privacy & Security. Running from terminal inherits the terminal's permissions; running as a standalone app (via `open`) requires its own grants. Accessibility is checked via `AXIsProcessTrusted()`. Input Monitoring is checked via `IOHIDCheckAccess(kIOHIDRequestTypeListenEvent)` (not a public Swift symbol — accessed via `dlsym`). The event tap (`CGEvent.tapCreate`) requires both permissions, so it can't distinguish which is missing on its own. Accessibility changes take effect immediately; Input Monitoring requires an app restart. A `DistributedNotificationCenter` observer on `com.apple.accessibility.api` detects Accessibility changes and tears down or re-creates the event tap. A safety timer backs this up in case neither that notification nor the tap-disabled callback fires: it ticks every 3s while something is wrong (tap down, or assigned but not re-enableable) and settles to a 30s heartbeat once the tap is verified, armed from launch by a final `accessibilityChanged()` call in `applicationDidFinishLaunching`.
- **Code signing**: Ad-hoc signed (`codesign --force --sign -`) so permissions persist across rebuilds (tied to bundle ID, not binary hash).
- **App hides from Dock**: Both `LSUIElement=true` in Info.plist and `.accessory` activation policy.
- **Menu bar background positioning**: macOS constrains normal windows below the menu bar area. `UnconstrainedWindow` overrides `constrainFrameRect(_:to:)` to bypass this. Windows must be created once and never destroyed to avoid position resets. Uses `NSApplication.didChangeScreenParametersNotification` to reposition when screen layout changes. Hides during Mission Control by checking for Dock-owned windows at layer > 0 in `CGWindowListCopyWindowInfo`.
- **Liquid Glass**: `NSGlassEffectView` is available on macOS 26. Style `1` (`NSGlassEffectView.Style(rawValue: 1)`) gives the "clear glass" variant. Use `contentView` property to embed content, not `addSubview`. `actool` compiles `Icon.icon` bundles from Icon Composer into `Assets.car`; requires full Xcode, not just CLT.
- **GNOME shortcuts app-aware gating**: Finder, Browsers, Terminal, and Code Editor category shortcuts only fire in matching apps. Browser apps: Safari, Firefox, Chrome, Edge, Brave, Opera, Vivaldi, Arc. Code editors: VS Code, Cursor, JetBrains, Zed, Sublime Text, Nova. The gated shortcut IDs are derived from the `allShortcuts` array filtered by category — adding a shortcut to any gated category automatically restricts it. `isEnabled()` checks both the disabled set and the app context. Ctrl+H contextually maps to Find and Replace (⌥⌘F) in code editors and View History (⌘Y) in browsers.
- **GNOME shortcuts terminal detection**: Reuses the same terminal bundle ID set as HomeEndHandler. In terminal apps, plain Ctrl+A/C/D/E/L/U/W/Z pass through unchanged since those are native terminal control sequences (⌃A is readline's beginning-of-line, the twin of the ⌃E that was always passed through). Ctrl+Shift+C/V/W/Q/T are remapped to Cmd equivalents (copy/paste/close/new tab in terminals); a disabled one passes the chord through rather than falling through to another category's mapping of it. All other Ctrl remaps still apply in terminals.
- **Finder cut & paste**: Handled by `FinderCutHandler`, separate from `GnomeShortcutHandler`. Ctrl+X posts Cmd+C and sets `cutPending` flag. Next Ctrl+V posts Cmd+Opt+V (move) only when the pasteboard change count is exactly +1 from the cut — Finder's copy always bumps it by exactly 1, so an unmoved count means the copy never landed (empty selection, slow volume) and a higher one means a copy happened somewhere the handler cannot see; either way the chord falls back to an ordinary Cmd+V paste. Ctrl+C clears the flag, as does an actual `finderCutMode` change (not unrelated preference writes). Only active in Finder when no text field is focused (renaming). Own UserDefaults key (`finderCutMode`, default off). Checked before GNOME shortcuts in event routing so Ctrl+X/V in Finder is intercepted first.
- **GNOME shortcuts per-shortcut toggles**: Disabled shortcut IDs stored in `gnomeDisabledShortcuts` UserDefaults array. `GnomeShortcutHandler.reloadSettings()` rebuilds the disabled set from UserDefaults. Settings UI uses `GnomeShortcutSettings` ObservableObject with per-ID bindings. Shortcuts organized into 9 categories displayed as DisclosureGroups with checkbox-style toggles (per HIG: checkboxes for hierarchical settings).
- **GNOME shortcuts are layout-aware**: key codes are physical positions, so any remap that *changes* keys (⌃Y → ⇧⌘Z, Alt+F4 → ⌘W, Alt+L → ⌃⌘Q, ⌃H → ⌥⌘F/⌘Y) would land on the wrong letter under QWERTZ/AZERTY, where the letters live at different positions. `KeyboardLayout.swift` translates between characters and key codes through the current keyboard layout (UCKeyTranslate, cached per input source, US ANSI as the fallback), the letter-keyed shortcut tables are matched by typed character and derived from the key-code tables through fixed US positions, and cross-key outputs resolve to the key that types the target letter. Same-key modifier swaps (⌃C → ⌘C) stay positional by design. ⌥A → Apps matches the typed `a` the same way.
- **⌥A → Apps**: Handled in AppDelegate's `handleKeyDown` as its own feature toggle (`appGridEnabled`), separate from GNOME shortcut remapping. Calls `triggerSpotlight()` (same as double-press Option). Checked before the GNOME shortcut handler in event routing.
- **Home/End in terminals**: CGEvents can't inject into a terminal's PTY. Terminal apps are skipped; users must configure Home/End in their terminal's keyboard settings and shell (`bindkey` in zsh).
- **Caret position is only available in some apps**: `MenuKeyHandler` locates the caret with `kAXBoundsForRangeParameterizedAttribute`. Firefox and native AppKit apps return a real caret rect (e.g. `1x17`). Chrome, Slack, and VS Code report success but return a degenerate `0x0` rect at `0,1080`, so the `caret.height > 0` guard is what makes them fall back instead of clicking at the top-left of the screen — **don't remove it**. Chromium and Electron apps additionally expose no focused element at all until `AXManualAccessibility` is set to true on the app element; doing so was measured to fix only GitHub Desktop (Slack and VS Code still return `0x0`, Chrome doesn't support the attribute), which is not worth enabling the full accessibility tree in every Electron app, so SuperOpt deliberately does not set it. `AXSelectedTextMarkerRange`/`AXBoundsForTextMarkerRange` are the untried alternative for Chromium.
- **VS Code integrated terminal detection**: Bundle ID alone can't tell VS Code's terminal from its editor, so `ElectronTerminalDetector` inspects the focused AX element. Chromium builds no accessibility tree until an assistive client asks for one, so the app's `AXManualAccessibility` attribute must be set to true first — without it the focused element query returns `kAXErrorNoValue`. That attribute always reads back as `0` even once it has taken effect, so which processes it was set on is tracked in memory instead of queried. The discriminator is the private `AXDOMClassList` attribute, which Chromium uses to expose an element's DOM classes: the terminal's focused element is xterm.js's hidden textarea, classed `xterm-helper-textarea`. Measured alternatives for the same panes — command palette and quick open are `input`, the editor is `native-edit-context`, the chat box is a hashed CSS-module name (`messageInput_cKsPxg`), list rows are `monaco-list-row` — so the class is unique to the terminal. **Don't match the accessibility label instead.** It is localised (`"Terminal {0}, {1}"` renders as `"终端 1，zsh"` in Chinese, per `terminalTextBoxAriaLabelNumberAndTitle` in VS Code's `terminalInstance.ts`), and it varies by state — there are separate strings for a stale environment and for a terminal with no title. Roles are no more stable: the editor reported `AXTextArea` in one build and `native-edit-context` in the next. A DOM class is neither translated nor user visible, and it comes from xterm.js rather than VS Code, so it holds for any editor embedding xterm.js. Off by default because enabling Chromium accessibility costs memory and CPU inside the editor. AX probe latency measured at 0.16 ms median / 1.58 ms max, cheap enough to run inline on the event tap without caching.
- **Click-through focus cannot be turned on from outside an app**: macOS decides per view, in `NSView.acceptsFirstMouse(for:)`. There is no system setting and no AX attribute for it, which is why apps ship their own toggles for it (IINA's "Accept first mouse click if not in focus") and why third-party answers to this are focus-follows-mouse instead. Withhold-focus-replay is the only route from outside: consume the `leftMouseDown` at the event tap, raise and focus the target window, then post a synthetic press once it is in front. Measured behavior with a purpose-built two-window probe app: with the feature off the probe's content view never sees the click (macOS swallows it); with it on the view gets `mouseDown` with `windowIsKey == true`, for another app's window and for a second window of the frontmost app alike, and a double-click still arrives as `clickCount` 1 then 2.
- **AppKit text views ignore middle clicks entirely**: `NSTextView` handles only `mouseDown` (left); `otherMouseDown` lands in `NSResponder`'s default no-op, so a middle click moves no caret, clears no selection, does nothing at all. This broke middle-click paste in every pure-AppKit app (TextEdit included) two ways at once: the "pass the click through to position the cursor" premise never held, and the text inserted afterwards replaced the still-active selection with itself — the paste was working all along, invisibly, as a no-op (verified with a logging `NSTextView` probe: `INSERTTEXT 'the q'` over a live "the q" selection leaves the string unchanged; a read-back showing the selection gone afterwards is the insert collapsing it, not the click clearing it). The fix is to consume the middle click and post a synthetic left click at the same point, which positions the caret natively; Chromium-style apps that implement middle clicks themselves only ever saw the feature for non-text-field targets, which pass through untouched.
- **Synthetic clicks do not activate windows**: the window server's activate-on-click runs only for real hardware events. A posted `otherMouseDown` (or any posted click) on an inactive window activates nothing — measured with the frontmost app unchanged after the post — which is also why `ClickThroughFocusHandler` calls `activate()` itself instead of relying on its replay. Any handler that replaces a real click with a synthetic one must do its own raise-and-focus first, or the replacement click is swallowed as a bare activation and reaches no view. A left click on an inactive window of the *frontmost app* is swallowed the same way — the two-browser-windows case.
- **The cursor window is the first window at the pointer in `CGWindowListCopyWindowInfo`**: a window at exactly `CGWindowLevelForKey(.cursorWindow)` (layer 2147483630) follows the pointer and therefore contains whatever point a hit test is resolving. A front-to-back hit test that bails on the first non-layer-0 window reports nothing whenever it is present (measured present after synthetic pointer moves, absent after warping elsewhere — situational, but it silently kills the whole hit test when there). `MiddleClickPasteWindow.frontWindow` skips it by level before the layer-0 guard; `ClickThroughFocusHandler.frontWindow` does the same.
- **A backgrounded Chromium app is invisible to the AX APIs that matter here**: its app-level `kAXFocusedUIElementAttribute` fails with `kAXErrorCannotComplete` (-25212), the system-wide one with -25204, and its window tree contains no text elements — while a backgrounded *AppKit* app answers the app-level query fine. `AXManualAccessibility` (Chromium's opt-in, set by `ElectronTerminalDetector`) does not change this: only a frontmost Chromium app answers the focused-element query, and its editors hit-test as plain `AXGroup`s even then. So a middle click into a backgrounded VS Code cannot be classified at tap time at all — the paste has to let the real click through (whose activation brings the app forward, as any real click does) and re-check in a poll once the app under the point is frontmost, opting it into `AXManualAccessibility` on the way. The Chromium focused editor's own frame is only the *current line* (measured 1156×18 for a wide editor) — its ancestor `AXGroup`s cover the editor viewport — so a "point inside the focused text element" check must walk the parent chain, stopping at the window, whose frame would cover the sidebar and tabs as well.
- **Chromium editors expose neither text nor selection through AX**: the focused `AXTextArea` is a focus-only shell — `kAXValueAttribute` and `kAXSelectedTextAttribute` read back empty even over a live ⌘A selection, and `kAXSelectedTextRangeAttribute` reports (0, 0) — and the focused window's tree contains no text element at all (18 elements for a VS Code window, none with a value). The only route to a Chromium selection is copying it: post ⌘C while the source still has focus, then paste the clipboard — X11 "autocopy" semantics. Gate the copy on the source being Chromium with the private `AXDOMClassList` attribute (answered `["native-edit-context"]` by VS Code's editor, `-25205` by AppKit elements), or a Finder source would get a ⌘C that copies the selected *files*. The copy races the target window's activation — a posted keystroke routes to whichever app is frontmost at delivery time, and a raise that lands first delivers the ⌘C to the wrong app (measured: the clipboard sentinel pasted instead of the selection) — so the paste waits for `NSPasteboard.general.changeCount` to move before raising the target. An unmoved count at the 300 ms timeout means nothing was selected, and the ordinary clipboard fallback proceeds — the same behavior an AppKit source with no selection gets, so a deliberate ⌘C followed by a middle click still pastes — while a count that moved *after* focus left the source copied the wrong selection, and the paste is abandoned rather than pasting it. Two traps found in review of the wait itself: the change count must be snapshotted *before* the ⌘C is posted (a fast copy landing in the gap forces a spurious full timeout), and the focused-editor bounds check must test the ancestor's *role* before its *frame* — ancestor frames are nested supersets, so a containment check run first matches the whole page before the AXWebArea stop is ever reached. A third: the copy's attribution — was focus still on the source when the count moved? — must be **latched at the moment the count moves**, not sampled when the paste waits, because the deferred path's wait begins only after focus has already shifted to the target window; sampling then rejects every correctly-landed copy (`CopyLatch` watches from click time for exactly this reason).
- **The withheld release matters as much as the withheld press**: a fast click releases before the target has finished activating. If only the press is withheld, the target receives a `leftMouseUp` with no matching `leftMouseDown`. `ClickThroughFocusHandler` therefore also consumes the release while a press is pending and sends its own release with the replay; a release that arrives while a `.replayed` obligation stands is consumed and re-posted behind the press, and only a release arriving after that obligation has been consumed passes untouched.
- **Title bar presses are not clicked through**: macOS already raises an inactive window from its title bar and lets the same gesture drag it. Withholding the press would replay it up to 250 ms late, after the drag had started. Presses within 28 pt of the window's top edge are passed through instead. This also leaves the traffic lights and `ZoomButtonHandler` alone.
- **Hit-testing a click target**: `CGWindowListCopyWindowInfo(.optionOnScreenOnly)` returns windows front to back, so the first one whose bounds contain the point is the one the click lands on — occlusion is already resolved. Only layer 0 is a click-through candidate: above it are the menu bar, the Dock, open menus and notifications, which all take a click while inactive already; below it is the desktop. Mission Control has to be excluded separately, because its shield covers everything but leaves every window in the list. Measured at 0.53 ms median / 0.73 ms p95 for the full hit test, warm — the one ~50 ms sample per process is the cold first call. Cheap enough to run inline on the event tap for a mouse down, and to repeat once a frame while waiting for focus (at 120 Hz that is 0.7 ms of an 8.3 ms frame, for at most 250 ms after a click on an inactive window).
- **A window can be resized from just outside its frame, and that band is not a click-through target**: a press a few points off a window's edge is a grab on that window's resize border, but `CGWindowListCopyWindowInfo` bounds stop at the frame, so the hit test used to fall through to whatever showed behind and click-through focused the wrong window mid-resize. `ClickThroughFocusHandler` therefore bails when the point is outside a layer-0 window but within `resizeBand` of it; front-to-back order means any window reaching the point that way is in front of the one the press would otherwise land on. **The band's real width cannot be measured from another process**: window frame dragging is run by the window server, which ignores posted events, so a synthesized drag never resizes anything (measured: no resize at any offset from 4 pt inside the frame to 14 pt outside, with the window key and the app active), and the resize cursor never reaches `NSCursor.currentSystem`, which reports `arrow` throughout the same sweep. The 8 pt constant is therefore chosen, not measured, and deliberately a little wide — it also covers the corner grab areas. The two failure modes are not symmetric: too narrow hijacks a resize the user has committed to, too wide only costs click-through in a thin band around other windows' edges. Verified with two overlapping windows and posted clicks: at 2/4/6 pt outside the front window the back window no longer takes focus, at 8 pt and beyond click-through still works, and corners behave the same as edges.
- **Replaying a press needs the target to still be in front**: `NSRunningApplication.activate()` raises the app's key window, not necessarily the one that was clicked, so the replay is gated on re-running the hit test and finding the same window ID on top. If focus never lands within 250 ms, the press is dropped rather than replayed at whatever is there now — that just leaves stock macOS behavior, where the click activated the window and did nothing else.
- **Secure input (password fields)**: When a browser focuses a password field, macOS enables secure event input, which completely disables the event tap. Keyboard events bypass all taps and go directly to the app. Shortcut remapping (Ctrl+V → ⌘V, etc.) does not work in password fields — this is a macOS security feature that cannot be bypassed. Users must press ⌘V to paste in password fields.
- **Event rewriting vs posting**: `GnomeShortcutHandler` and `HomeEndHandler` rewrite the original CGEvent in-place (`KeyboardUtils.rewriteEvent`) instead of consuming it and posting a new one. This keeps the event in the normal pipeline. The callback returns the modified event when it has the synthetic tag, or nil when the event was consumed (e.g. dock launch). `FinderCutHandler` still uses `postKey` because it changes the key (Ctrl+X posts ⌘C) and needs the original consumed. `postKey` is also used for actions unrelated to the current keypress.
- **Synthetic event tagging**: `KeyboardUtils.rewriteEvent` and `postKey` both tag events with `eventSourceUserData = 0x4F5054`. `AppDelegate.handleKeyDown` skips synthetic events (`KeyboardUtils.isSynthetic`) so remapped keys (e.g. Ctrl+Left → ⌥Left) don't trigger other handlers (e.g. window tiling) when they re-enter the event tap.
- **Event tap threading**: The CGEventTap callback runs on the main run loop because `CFRunLoopAddSource` is called with `CFRunLoopGetCurrent()` from `applicationDidFinishLaunching` (main thread). UI calls in the callback are safe without dispatching to main.
- **Privacy keys**: Info.plist must include `NSAccessibilityUsageDescription` and `NSListenEventUsageDescription` for Accessibility and Input Monitoring permissions.
- **Ripple window level**: Must use `.screenSaver` (not `.floating`) so the ripple renders above the menu bar. `.floating` renders below it.
- **Mission Control close buttons**: Uses `CGSGetScreenRectForWindow` private API (via `dlsym` from SkyLight) to get the on-screen compositor bounds of windows during MC — unlike `CGWindowListCopyWindowInfo` bounds which report logical positions, this returns the actual thumbnail positions after MC's scaling transform. `_AXUIElementGetWindow` (from ApplicationServices) maps AX window elements to CGWindowIDs for exact matching. Click interception happens at the CGEvent tap level (`handleMouseDown` in AppDelegate) so the event is consumed before the Dock can interpret it as a window focus. The close button overlay uses `.screenSaver` window level, `ignoresMouseEvents = true` (purely visual — the event tap handles clicks). The shared monitor's tick updates hover and position while thumbnails are stable. A separate timer follows a newly hovered or moving thumbnail at the display refresh rate and stops when hover ends or its position has been stable for 2 seconds. **No timer runs while Mission Control is closed.** Polling starts from `noteMissionControlTrigger()`, which `AppDelegate` calls when it triggers Mission Control itself or when the event tap sees the Mission Control key (key code 160) pressed, and gives up after a 2s `graceWindow` if Mission Control never appears. It also starts when a mouse move happens to discover Mission Control already open. While ticking, hover is recomputed from the current pointer position rather than from mouse-moved events, because entering or leaving Mission Control with the pointer held still generates no mouse-moved event — a tap hook alone would neither raise the button on the way in nor clear it on the way out. Opening Mission Control with a trackpad swipe emits neither a key event nor a mouse move, so the button only appears once the pointer moves. That is an accepted trade rather than a bug: swiping means a hand is already on a pointing device, so a mouse move follows almost immediately. Covering it would mean either polling whenever the feature is enabled or adding gesture event types to the tap, neither of which is worth it. Ghost window handling was removed for macOS 27: on macOS 26, closing a background app's window left MC still showing its thumbnail while `CGWindowListCopyWindowInfo` no longer reported it, so the handler captured the rect and swallowed clicks and mouse moves over it (plus nudged the cursor off to clear the hover highlight). macOS 27 removes the stale thumbnail on its own, so none of that is needed — if orphaned thumbnails ever reappear, that is the history to look up.
- **The Spotlight key is key code 177 with the Fn flag**: captured from the hardware key with a listen-only tap, same shape as the Mission Control key (160) and Apps key (131). It toggles, and it opens the panel drawn by `com.apple.campo` (Siri AI.app). There is still no public API to open Spotlight — see the Apps key notes above for why the `spotlight:` URL scheme is a dead end on macOS 27.
- **Mission Control swallows the Spotlight key**: posting 177 (or 131) while Mission Control is on screen does nothing at all, so type-to-search has to dismiss Mission Control first and leave a gap before the Spotlight key. It does **not** have to wait out the close animation — the Mission Control window lingers ~320 ms, far longer than needed. Measured success rate by gap: **0 ms 0/8, 1–5 ms 0/8, 8 ms 3/8, 12 ms 6/8, 20 ms 23/23, 25/30/40 ms 15/15 each.** `MissionControlSearchHandler.dismissDelay` is 25 ms, twice the last gap that ever failed. Beware small samples here: an early 3-trial run showed 10 ms passing 3/3, which 8 trials contradicted. Spotlight is then ready ~140 ms after its key for search and ~175 ms for Apps.
- **Don't release the keyboard intercept the moment the text is posted**: a key pressed during the handoff can reach Spotlight ahead of the injected text, so typing "hi there" lands as "ehi ther" (observed 2/4 runs before the fix). `MissionControlSearchHandler` keeps consuming keys until the injected text is visible in Spotlight's field *and* nothing new is buffered, flushing any tail before it lets go. The first chunk's landed check tests that the field is non-empty — Spotlight opens empty, so anything means the text arrived, and exact matching would break if Spotlight ever completed the query. Later chunks and deletes-only flushes cannot use that check, so their landing is confirmed by the field's value *changing* from what it read at flush time — a change to empty counts too, since deletes shrink the field — and an unchanged value falls back to a deadline that every post refreshes, so it bounds one wait (for readiness, or for a landing) rather than the whole typing session. Nothing new is posted while a post is in flight: a second post sharing one snapshot would release the intercept on the first one's landing with the second still airborne, and a re-snapshot taken before the first landed would not include it. Deletes that find a non-empty field go out one at a time, each awaited for its own landing — backspaces are separate key events that arrive one at a time, so a batch posted together would confirm on the first one's landing with the rest still airborne — and text queued behind them waits for the last; deletes that find an empty field cannot change it and so share the text's snapshot (or end the session alone). A field read that fails is never a landing: nil is not a change, and a failed snapshot defers the post rather than sending it blind.
- **Spotlight's window is hidden by alpha, not by ordering out**: `com.apple.campo` keeps its panel window (same window number) across sessions and sets `kCGWindowAlpha` to 0 when Spotlight is dismissed — at which point the window also drops out of `.optionOnScreenOnly`. Checking only for an on-screen campo window is therefore not enough on its own, and checking only for a focused campo text field is worse, because that field *stays* focused after dismissal. `isSpotlightReady()` requires both, plus alpha > 0. Getting this wrong shows up as an alternating pass/fail pattern, because the Spotlight key toggles: a stale "already open" reading makes the next press close Spotlight instead of opening it.
- **Escape in Spotlight needs two presses**: the first clears the query, the second closes the panel. Worth knowing when scripting against it — a single Escape in a test harness leaves Spotlight open and desynchronizes the toggle.
- **Measure the window list walk spaced out, not in a loop**: benchmarking `CGWindowListCopyWindowInfo` plus `isMissionControlActive` in a tight loop gives 0.160 ms median / 0.327 ms p95, which flatters it badly — the loop keeps the path warm. Called once every 100 ms, the way a keystroke hook would, the same work costs **1.172 ms median / 3.912 ms p95 / 6.467 ms max**, roughly 7× the loop figure. That is why type-to-search does not simply probe on every keystroke, and why the shared `MissionControlMonitor` exists.
- **Mission Control state is tracked once, in `MissionControlMonitor`**: Dynamic Spaces requests a 1 Hz visibility check while idle so a trackpad swipe or rebound shortcut with the pointer held still is detected. Its desktop queries and AX actions run only when Mission Control is visible. On macOS 27.2.1 the Dock accepted registration for `AXExposeShowAllWindows` and `AXExposeExit`, but neither was delivered during a verified Mission Control key open and Escape close. The frame-rate trigger deadline still expires when the window list cannot be read. For the other consumers, the monitor is already polling whenever Mission Control was opened a way SuperOpt can see (the Mission Control key, the Option press, the hot corner), so type-to-search reads `isActive` for free. Only a Mission Control opened without a trigger (a trackpad swipe) needs the walk, paid at most once per typing burst.
- **Poll fast between the trigger and Mission Control arriving**: at the steady 4 Hz rate, `isActive` stays wrong for up to 250 ms after a trigger — the entire opening animation. Anything reading it in that window silently misses. Measured with type-to-search: keys typed 0–240 ms after the Mission Control key, while already mid-typing, were dropped outright (at 200–240 ms the *first* character went missing and the query arrived as `"i"` instead of `"hi"`); only from 300 ms did it work. `MissionControlMonitor` therefore polls at the display refresh rate from `noteTrigger()` until Mission Control appears, then drops to 4 Hz, and exposes `isOpening` so a caller mid-animation can force a check rather than wait. After the fix the same sweep passes from 20 ms onward. The residual 0–15 ms window is inherent: Mission Control is not on screen yet (it becomes detectable 28–89 ms after the key is pressed), so the keystroke belongs to the app underneath.
- **A fresh typing burst hid this bug**: the same sweep with no keystroke immediately before the Mission Control key passed at every delay, because the burst throttle let the fallback probe run. The failure only shows when Mission Control is opened *mid-typing*, within 300 ms of the previous key — test it that way.
- **`isActive` is not enough to tell one Mission Control from the next**: it stays true through the ~320 ms close animation. Type-to-search dismisses Mission Control and then keeps receiving the tail of the user's typing, so without a guard a late keystroke sees `isActive == true`, starts a second search, and the second Mission Control key press toggles it back *open*. `MissionControlMonitor.activationID` increments on each inactive→active transition and `MissionControlSearchHandler` runs one search per ID. The old per-keystroke throttle hid this bug by accident. Clicks are suppressed by time rather than by marking the activation: both the press and its release stamp a 0.4 s window in which no session may start, and a keystroke rejected by it does not count as typing, so the cost is confined to the window — a click that leaves Mission Control open (the spaces bar) costs at most that window, and a close-button hit stamps nothing at all, staying fully searchable. The stamp is taken for every real (non-synthetic) non-close-button press, not only while the monitor reports Mission Control up, because a swipe-opened Mission Control it has not seen yet is closed by the same click.
- **Buffered keystrokes are injected as text, not as key codes**: `KeyboardUtils.postText` posts one event pair carrying a Unicode payload via `keyboardSetUnicodeString`. Replaying the original key codes would be wrong, since the characters were produced under whatever layout was active at the time. Verified landing in Spotlight's `AXTextField`.
- **The tiling menu items moved deeper in macOS 27**: `Window > Move & Resize >` now wraps the half-screen items, so Left/Right/Top/Bottom and Return to Previous Size sit at depth 5 measured from the menu bar, while Fill and Centre stay at depth 3. `KeyboardUtilsMenus.searchDepth` was exactly 5, so tiling worked with no margin at all and one more level of nesting would have broken it silently; it is 8 now. The search stops at the first match, so the larger ceiling costs nothing. macOS 27 also exposes Top and Bottom halves (virtual keys 126 and 125, modifier 28) and Left & Right / Top & Bottom arrange pairs (modifier 29), which SuperOpt does not use yet.
- **Mission Control detection**: `KeyboardUtils.isMissionControlActive` looks for a `WindowManager`-owned window at layer >0 that fills a whole display. Shared by `MenuBarBackground` and `MissionControlCloseHandler`. On macOS 27 Mission Control is drawn by the **`WindowManager`** process, not the Dock: it adds an `ExposeShieldWindow` per display (layer 19, full screen), a `Spaces Bar` strip (layer 14), and transient `Window Highlight Overlay` windows. No `WindowManager` window is on screen when Mission Control is closed. The match is structural (owner + layer + size) rather than on the `ExposeShieldWindow` name, because `kCGWindowName` is only populated for other processes when the caller holds **Screen Recording** permission, which this app never requests — window owner, layer, and bounds need no such permission.
- **Don't count Dock windows to detect Mission Control**: the old heuristic (">1 Dock-owned window at layer >0") is dead on macOS 27 and silently returns false in *every* configuration, disabling the Mission Control close buttons and `MenuBarBackground`'s hide-during-MC behavior. The Dock is now a single full-display-sized window whose `CGWindowListCopyWindowInfo` entry is byte-identical whether or not Mission Control is open, and with "Automatically hide and show the Dock" enabled it has no on-screen window at all. Window *size* is likewise not a Dock discriminator any more — the Dock's window is full-screen, not a strip along one edge.

## Code Signing

The signing identity is read from `CODESIGN_IDENTITY` in `.env` (local) or environment variable (CI). Falls back to ad-hoc signing (`-`) when no identity is configured. Using a stable certificate preserves TCC permissions (Accessibility, Input Monitoring) across rebuilds and updates.

## CI

GitHub Actions workflow at `.github/workflows/release.yml` — triggers on `x.y.z` tags, builds on `xcode-27`, creates a GitHub release with `SuperOpt.zip` attached. Release notes are generated from `git log` since the previous tag. The CI imports a signing certificate from repository secrets (`CODESIGN_P12`, `CODESIGN_P12_PASSWORD`, `CODESIGN_IDENTITY`) into a temporary keychain for code signing. After the release, the workflow auto-updates the Homebrew cask (`Casks/superopt.rb`) with the new version and SHA via the GraphQL API (signed commit), then triggers a `repository_dispatch` to `logonoff/homebrew-bucket` to sync the cask there too.

A `Makefile` is also available with targets: `build`, `install` (moves to /Applications, building first if needed), `run` (kill → clean → install → open; see Build & Install), `kill`, `clean`.

## Homebrew

A cask is hosted in this repo at `Casks/superopt.rb` and mirrored to `logonoff/homebrew-bucket`. Install via:

```bash
brew install --cask logonoff/bucket/superopt
```
